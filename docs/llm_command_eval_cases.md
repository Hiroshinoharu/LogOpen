# LLM diagnostic command evaluation cases

This document records real failures observed while manually testing Windows
diagnostic commands generated by LogOpen's LLM. Keep these cases to improve
instructions and support future automated evaluation and regression tests.

This is an evaluation log. LogOpen must not automatically execute these commands.
Safer alternatives below are candidates for review and retesting, not recorded
successful retests.

Use the same fields and a new sequential case ID for each future failure. Statuses
are **Open**, **Prompt updated**, **Retest required**, and **Resolved**. A prompt
update alone does not resolve a case.

## LLM-CMD-001 — Invalid Windows Event Provider assumption

**Case ID:** LLM-CMD-001

**Incident/context:** System log, Event ID 10010; LogOpen supplied/displayed the
provider label `DCOM`.

**Generated command:**

```powershell
Get-WinEvent -FilterHashtable @{LogName='System'; Id=10010; ProviderName='DCOM'} |
    Select-Object -First 50 TimeCreated, Id, ProviderName, LevelDisplayName, Message
```

**Expected diagnostic purpose:** Inspect up to 50 events related to the reported
DCOM incident, including their timestamps, provider information, and messages.

**Actual result:** PowerShell reported that there was no registered event provider
matching "DCOM".

**Failure category:** Unsupported identifier assumption

**Why it failed:** The LLM assumed LogOpen's provider/display label could be passed
directly to `Get-WinEvent` as a registered `ProviderName`.

**Prompt/instruction improvement:** Do not assume LogOpen/display provider labels
are registered Windows Event Provider names. If the evidence does not establish
the exact registered provider name, omit `ProviderName` and use evidenced filters
such as log name and Event ID. Do not guess a replacement provider name.

**Safer alternative:**

```powershell
Get-WinEvent -FilterHashtable @{LogName='System'; Id=10010} |
    Select-Object -First 50 TimeCreated, Id, ProviderName, LevelDisplayName, Message
```

**Status:** Retest required

## LLM-CMD-002 — Unnecessary elevated AppX query

**Case ID:** LLM-CMD-002

**Incident/context:** Inspection of `MicrosoftWindows.Client.CBS` package
information from a normal, non-elevated PowerShell session. Further incident
details were not supplied in this failure report.

**Generated command:**

```powershell
Get-AppxPackage -AllUsers |
    Where-Object {$_.PackageFullName -like 'MicrosoftWindows.Client.CBS*'} |
    Select-Object Name, PackageFullName, Version, Status
```

**Expected diagnostic purpose:** Inspect the package's identity, version, and
status to gather information relevant to the incident.

**Actual result:** Access denied / `UnauthorizedAccessException` when executed
from a normal PowerShell session.

**Failure category:** Unnecessary privilege requirement

**Why it failed:** The LLM selected the elevated `-AllUsers` scope even though
inspecting the current user's package information may have been sufficient for
the diagnostic objective.

**Prompt/instruction improvement:** Follow least privilege. Prefer commands that
work without administrator privileges and avoid system-wide switches such as
`-AllUsers` unless the evidence and diagnostic objective require them. If elevation
is necessary, explicitly explain that requirement in the step description.

**Safer alternative:**

```powershell
Get-AppxPackage |
    Where-Object {$_.PackageFullName -like 'MicrosoftWindows.Client.CBS*'} |
    Select-Object Name, PackageFullName, Version, Status
```

**Status:** Retest required

## LLM-CMD-003 — Unsupported PnP device-class assumption

**Case ID:** LLM-CMD-003

**Incident/context:** Investigation involving security hardware; the appropriate
Windows PnP device class on the machine had not been established. Further incident
details were not supplied in this failure report.

**Generated command:**

```powershell
Get-PnpDevice -Class Security -PresentOnly |
    Select-Object Status, Class, FriendlyName, InstanceId
```

**Expected diagnostic purpose:** Inspect present devices relevant to the hardware
investigation, including their status, class, name, and instance ID.

**Actual result:** `Get-PnpDevice` returned no matching `Win32_PnPEntity` objects
for `PNPClass` "Security".

**Failure category:** Unsupported identifier/filter assumption

**Why it failed:** The LLM converted the natural-language concept of security
hardware into an exact Windows PnP class value without evidence that `Security`
was a valid class present on this machine. The result does not establish that
security hardware is absent or that the class name is invalid on every system.

**Prompt/instruction improvement:** Do not convert natural-language concepts into
exact Windows identifiers, such as device classes, provider names, service names,
package identifiers, driver names, registry paths, or process names, unless the
mapping is established by supplied evidence. Prefer discovery before applying an
uncertain machine-specific filter.

**Safer alternative:**

```powershell
Get-PnpDevice -PresentOnly |
    Select-Object Status, Class, FriendlyName, InstanceId
```

Use the broader discovery query first when the appropriate machine-specific class
is unknown; use its results to inform any later filter.

**Status:** Retest required

## Regression process

1. Generate diagnostic steps from a representative real incident.
2. Review the commands before execution.
3. Manually execute only commands considered safe.
4. Record failures in this document using the case fields above.
5. Identify the assumption that caused each failure.
6. Improve the LLM instructions where appropriate.
7. Generate a new analysis for the same or an equivalent incident.
8. Retest the newly generated command and record the command, context, and outcome
   in the case.
9. Mark the case **Resolved** only when retesting shows that the problematic
   behavior no longer occurs.
10. Keep resolved cases in this document as regression examples.

## General failure categories

Extend this list as testing continues; a case may involve multiple categories.

- Unsupported identifier assumption
- Unsupported filter assumption
- Unnecessary privilege requirement
- Invalid command or parameter
- Incorrect risk classification
- Unsupported system-state assumption
- Potentially unsafe recommendation
- Command does not achieve diagnostic objective
